# 从项目经验提炼知识库

目标：让另一个项目的Agent知道先做什么、什么方法值得试、典型数值和成本怎样、哪些地方不能想当然，而不是把项目日志换个目录。

适用于开发、科研、性能与工具项目；不限定领域。先复用已有证据，不为整理知识库重跑实验或扩研究范围。

## 1. 找到值得迁移的材料

- 从用户目标、当前交付和已有知识库入手；能补充同主题kb-*就不另建重叠库。
- 用`load-mem`回收相关背景，按线索查报告、配置、结果表、决策、journal、Git和历史消息；有记忆工具时主动查真实踩坑与更正，不只读README或最终成功报告。
- 旧Agent标出的“必须记住／不要再犯／已撤销”是高价值线索，直接提取其已有证据，不无故重做调查。
- 这些标记不自动证明因果或当前有效；对重要数字、配置和修复，找到对应结果或当前记录。旧错误保留为反例，更正另标清楚。
- 沿相关线索补齐即可；不全库倾倒、不要求每个记忆系统都搜一轮。缺来源或资料不可访问，标明缺口。
- 外部资料有用则连同固定版本、出处与原文/许可条件保留；区分外部报告与本项目复现，不把文献数字写成本地成绩。

完成标志：已找到能指导相似任务的材料及来源，也知道哪些只是状态、猜测或已失效记录。

## 2. 判断价值，不按篇幅或新奇程度筛

核心问题：**拿掉这条，下一位Agent是否容易选错、漏条件、估错收益/成本，或重踩已发生的坑？**

| 候选内容 | 保留建议 |
|---|---|
| 有效方法、关键决策及适用/失效条件 | 优先；解释何时选、为何选、何时停止或换路 |
| 经典结果、完整配置、经验范围、离线/在线成本 | 优先；带baseline、协议、单位和证据，不只留最好数字 |
| 阴性结果、不起效的组合、已纠正的错误解释 | 优先；能省下重复尝试或约束结论，就是经验 |
| 已真实踩过的坑、反直觉现象、易混轴/键名/接口行为 | 优先；即使概念简单或只发生一次，也可很昂贵 |
| 基础知识 | 能防真实误用、读懂后续配置所必需时简写；否则略过，不写教科书 |
| 待验证猜测 | 有明确后续判断价值才留，单列未验证；不包装成规律 |
| 进程/PID、临时目录、一次性操作流水 | 留项目记忆；提炼可迁移教训，不带走运行状态 |
| 无差异点的常识、重复记录、无用途的碎片 | 合并或舍弃；不为“完整”照单全收 |

- 宁可把有价值的长尾放reference，也不为入口短而丢条件、反例或经典数值；不机械只留top几条。
- “历史被记过”是优先线索，不是必须照抄；合并重复项，核对更正，保留可操作细节。
- “项目特定”不等于不能迁移：模型/硬件/版本可作为案例条件保留，个人路径、身份、凭据和运行状态不作通用知识。
- 一个案例是经验锚点，不是总体规律；只有同条件重复或多例支持，才谈范围和趋势。机制事实、实测、推断分别写。

完成标志：每个建议保留的主题都有用途与具体内容；舍弃理由不是“太基础”“只出现一次”这类机械标签。

## 3. 给建议，让用户补漏确认

先在聊天里给一轮按主题合并的短清单，不先写完整知识库或另建评审文档：

| 建议主题 | 拟保留的具体经验/数值/配置 | 迁移价值与证据边界 |
|---|---|---|
| 已验方法与结果 | 代表配方、相对基线、成本、失效组合 | 给新任务选路与估预期；标明验证范围 |
| 真实踩坑与诊断 | 症状→根因/未知→修正→复验 | 防止重踩，保留容易想当然的细节 |
| 配置与参考 | 最小有效配置、关键开关、外部资料 | 能照着开始，而非只有结论 |

表格只是结构示意；替换成项目的真实内容，不拿空泛分类让用户自己找材料。简短列出建议不带走的内容和重要缺口。

- 给明确推荐，不把所有条目都变成问题；通常问一句：“建议保留这些。哪些要删，哪些重要经验我漏了？”
- 等用户确认、删补或明确委托你判断后，再成库；“默认多保留”不是把沉默当确认。
- 用户已明确选定材料/范围时复用该确认，不再问一遍。新出现的范围、敏感资料或影响结论的缺口再讨论。
- 用户补充的经历也标来源与证据等级；认可某结论不能代替实测或消除不确定性。

完成标志：保留主题与范围已对齐，用户有实际补漏机会；普通命名、排版和拆文件由Agent决定。

## 4. 确认后联动writing-skill成库

此时加载`writing-skill`，按其命名、维护归属、description、短入口与附属文件规则制作/更新；文字遵循`readable-docs`。不重复设计一套写作/安装规范。

- 入口面向新任务：何时用、第一步查什么、如何选路、哪些误用先排查、何时转其他skill；不是项目年表。
- reference按需容纳经验规律、成功/失败路径、诊断与外部证据；完整配置、可计算表格和必要小样本放assets，不强制每库凑齐目录。
- 数值随比较合同保存：对象/版本、算法与关键配置、baseline、数据/样本/种子、指标/单位、结果和适用边界；性能另带硬件、负载、计时范围与成本。
- 不同比较组分开；粒度、后端、样本或预处理同时变化，称组合结果，不把全部增益归给一个因素。缺字段标未知，不填想当然默认值。
- 踩坑写到能行动：什么症状、错在哪、如何识别/修正、怎样验过；根因未明就保留未知，不编解释。
- 不只留“做什么”：保留关键先后顺序、参数关系、正确广播/归约轴、共享分支、缓存失效等真正易错条件。
- 相对引用要落到随包文件；关键理解不能只靠本机路径、私有会话或记忆ID。原始大工件可留项目，库内保留必要摘要、出处与未打包边界。

完成标志：新Agent不依赖原会话也能据此开始相似任务；经验仍带条件，没有变成无依据的普遍承诺。

## 5. 用真实案例走读，再交付

- 选已有代表性案例走一遍入口：能找到起步配置、预期量级、已知反例和诊断路径；无需重跑原实验。
- 抽查重要数值及配置与原记录一致，失败/撤销项不再作为正面证据；“可加载”不等于内容正确或跨项目效果已证实。
- 按`writing-skill`检查触发、格式、相对引用和去情境化；涉及敏感/不可分发原文先处理，不把历史中的凭据带走。
- 在约定位置交付整目录，按需附迁移包；更新已有库保留用户修改和证据演变，不覆盖陌生内容。
- 告知库名/位置、主要覆盖、未核实/未打包内容即可。新实验和更大知识体系不是默认收尾工作。

完成标志：内容、可移植性与实际交付均已检查；未验证边界诚实保留。

## 维护

本流程只随真实漏筛、过筛、遗漏或误迁移反馈做小修；具体领域的新经验更新目标kb-*，不堆进本流程。
