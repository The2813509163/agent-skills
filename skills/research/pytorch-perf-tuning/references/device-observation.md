# PyTorch 设备使用情况：观测与判断

## 目标：有效工作多，无意义等待少

算法原型允许保留复杂控制流和真正的数据依赖；评测／推理应尽量消除无意义同步、串行、搬运和冗余计算。评价单位是目标任务及其执行阶段，不能只看代码行数或硬件读数。

“利用率高、功率高、有效内存多、冗余驻留少”是有用线索；最终看同协议有效吞吐、延迟和等待是否改善。忙着算 padding、重复计算或搬运也能让设备很忙；更好的实现可能更快、功率更低、显存更少。

## 一次短窗口够用的观测

先确认 PID、物理卡号／UUID、可见设备映射与其他进程。用已有或下一次真实小样本运行，分别标出加载、准备、预热、评分／生成；不要为了填表启动全量任务。

| 观测 | 记录与解释 |
|---|---|
| 有效工作 | 有效 tokens/s、samples/s 或候选/s，host 总时长／评分时长；排除 padding，不混用 prefill 与 decode 口径 |
| 设备忙碌度 | GPU utilization 或 NPU AICore／AIVector／AICPU，保留字段原名与采样窗口；多卡分别记录 |
| 功率与运行状态 | W；可用时加功率限制、温度、时钟。看同卡同阶段波动，不跨型号按瓦数排名 |
| 内存容量 | 设备／进程占用、torch allocated/reserved 及峰值；区分必要权重、有效激活／KV、冗余驻留 |
| 内存活动 | 可用时记录 HBM 带宽利用率；GPU memory utilization 的定义按驱动确认，不能当显存容量或直接当峰值带宽比例 |
| 等待线索 | 设备低忙碌区间是否对应 CPU 准备、I/O、同步或串行下发；原因不清才用短 profiler |

- 默认在旁路进程约每1–2秒采样一个代表性窗口，保存时间戳、原值和阶段；给出均值／范围与明显低忙碌区间即可。工具自身查询很慢时降低频率。
- 短于采样周期的片段不能由系统监控定性，转用现成 Event100／短 trace；不为凑硬件读数反复延长实验。
- 监控不进入模型热循环，不调用设备同步取指标；正式 A/B 使用一致的监控方式，结束后停止本次采样进程。
- 系统忙碌度不等于峰值 FLOPS 利用率，也不等于 kernel occupancy。NPU Vector 工作不能只用 AICore 一列判断；字段不支持就标缺失，不假设为零。
- 功率含设备基础功耗；单次快照、其他作业、温度／功率限制都可能误导。仅凭“低功率”不能判定 Python 没喂饱设备。

## 可直接取用的命令

### NVIDIA 模板

将 `GPU_ID` 设为目标物理卡号或 UUID；字段以本机 `nvidia-smi --help-query-gpu` 为准。此模板未在本轮 Ascend 主机上实测。

```bash
nvidia-smi --query-gpu=timestamp,index,uuid,utilization.gpu,utilization.memory,power.draw,power.limit,memory.used,memory.total,temperature.gpu --format=csv -i "$GPU_ID" -l 1
```

卡级读数用 `nvidia-smi` 的进程列表辅助归属；多租户／MIG 环境核对指标范围。CUDA_VISIBLE_DEVICES 的逻辑序号不直接当物理卡号。

### Ascend 只读查询

以下命令在2026-10-19的910B2主机实测可用；`CARD`、`CHIP` 换成实际映射，其他版本先看 `npu-smi info -h`。独立采样器可周期调用并附时间戳，不修改功率／频率设置。

```bash
npu-smi info
npu-smi info -m
npu-smi info -t usages -i "$CARD" -c "$CHIP"
npu-smi info -t power -i "$CARD" -c "$CHIP"
npu-smi info -t memory -i "$CARD" -c "$CHIP"
npu-smi info -t temp -i "$CARD" -c "$CHIP"
```

该版本 `usages` 包含 AICore、AIVector、AICPU、HBM Usage Rate 和 HBM Bandwidth Usage Rate。后两项分别是容量与带宽，不能混淆。ASCEND_RT_VISIBLE_DEVICES 的逻辑设备映射须单独核对。

## 从信号到结论：只做最小区分实验

| 共同观察 | 首先怀疑 | 低成本证据 |
|---|---|---|
| 评分慢、设备反复低忙碌，host 长段等待 | `.item()`／动态索引同步、CPU 准备、逐项串行 | 选一个真实输入，看相应热路径或短 trace；去掉一个确定同步点后配对测速 |
| 大量小 kernel、吞吐低 | 下发碎片、逐专家／逐 token 循环 | 复用 grouped／批量路径或融合一个稳定片段，比较整段时间 |
| 算力忙碌度低、HBM 活动高 | 带宽或算术强度限制 | 同输入少量 batch／布局对照；不要因功率低就定性为浪费 |
| AICore低、AIVector高，伪量化明显慢于浮点参考 | 归约、舍入／重建等向量处理及临时张量 | 固定分组／后端看完整链；计数器不是某个算子的精确耗时占比 |
| 多卡一张忙、其他空闲 | 分片不均、顺序模型并行、依赖／通信 | 核对模型放置和每卡阶段；确有独立工作才尝试并行 |
| 占用高却吞吐低 | 必要模型容量，也可能是重复权重、无用KV／logits | 按 storage 去重，列张量用途；释放确定冗余后才试更合适 batch |
| 利用率／功率高，吞吐却差 | 冗余计算、padding、重复搬运或低效核 | 看有效 token 比例和实际执行链；高读数不能免除这项检查 |
| 小 batch、自回归依赖，且未见明显等待 | 工作量不足或算法／协议的合理限制 | 核对依赖；只在允许的同协议内做少量 batch 对照，不能为了占满卡改变算法 |

不能靠架构名称、MoE 或“算法原型”推断天然低效；也不因正常带宽／依赖限制强迫重写算法。最小证据不足时写“待定位”，不自动进入极限调优。

## 大矩阵压测与长输入：回答不同问题

- 固定大GEMM连续重放，计算密集、形状稳定、额外工作少；可验证设备持续计算与监控显示能力。近满载不是整模应达到的及格线，也不是峰值FLOPS百分比。
- 模型含归约、路由、访存、依赖和评分；短输入／稀疏专家可能形成许多小矩阵。不能把总参数量、配置batch上限或配置max_length当实际计算规模。
- 采集实际batch、有效长度、每专家收到的行数及GEMM的M/N/K，而不是只看总体tensor元素数；grouped GEMM减少下发，不保证每个专家都有足够大的矩阵。
- 伪量化通常增加动态统计、舍入和重建，后续GEMM仍用原浮点dtype；没有自动获得真实低位部署的计算／存储收益。低AICore不能单独评价格式、量化算法或引擎潜力。

只有规模假设会改变下一步时，取少量真实文本的嵌套前缀，固定batch、模型、定标、后端与调度，做短长度对照；已有合适证据则复用。若要区分量化附加开销，可加入浮点参考，不能默认扩展成全模型／全格式矩阵。

| 观察 | 可支持的解释与边界 |
|---|---|
| 长度增加，忙碌度与有效token/s一起提高 | 小工作量是影响因素；输入与路由也变了，不等于已隔离某一个GEMM |
| 更长时AIVector／HBM更忙，token/s下降 | 工作组成或资源压力改变；Attention随长度增长，具体占比需额外证据，不能仅凭采样断言根因 |
| 浮点参考改善，伪量化仍低AICore且高Vector | 不只是矩阵规模；仅当仍阻塞研究时定位量化热路径 |
| 大临时统计张量OOM | 区分活张量峰值、最大路由容量补零、缓存／碎片；不直接降batch或修改定标掩盖问题 |

- 规模探针改变了工作负载，只能说明规模响应；固定输入热重放不冒充harness吞吐。不为提高利用率给短题加长文本、扩大无用padding或重复计算。
- 显存分配策略重试先核对平台支持，记录环境、形状历史与一个短锚点；新进程跑通不能证明所有reserved差额都是碎片。不能把OOM组计为完成。
- 结论足以区分“浪费／合理受限／证据不足”且等待已可接受就收口；专业引擎也不保证所有负载满载，残余低利用率本身不启动新优化。

## 内存用途与收口

- 必要驻留：唯一权重、当前所需激活／KV、确实需要的工作区及可复用缓存；不会因暂时没有计算就成为“死内存”。
- 冗余驻留：无后续用途仍被引用的张量、可去重的权重副本、纯打分不需要的KV、无用完整 logits 等；须说明对象、字节和用途证据。
- `allocated` 也可能含冗余活张量；`reserved−allocated` 含缓存与碎片，不是可直接删除的“死内存总量”。系统进程显存还可能含框架外分配。
- 不以占满显存或功率上限为目标。先去掉浪费，余量能改善有效 batch 就利用，不能改善时保留余量也合理。
- 报告只需：同阶段指标、一个结论（可避免浪费／当前口径合理受限／证据不足）、依据、一次低成本改动结果。正确且可靠地缩短等待后收口。
